## 01 — IaaS、PaaS、SaaS 基础概念

```text
原创中文技术知识卡片，3:4 竖版（约 1536×2048），浅米白背景，现代云计算信息图风格，深蓝与青绿色为主色、少量橙色强调，圆角卡片，清晰矢量感图标，手机端可读，留白充足。不要品牌 Logo，不要人物照片，不要页码，不要水印。所有中文、英文缩写、大小写必须准确。

主标题：IaaS、PaaS、SaaS
副标题：你到底“租”到了哪一层？

画面中心为三列从左到右的服务层级对比，每列有简洁建筑分层/积木图标与一句白话：

第一列：
IaaS
Infrastructure as a Service
基础设施即服务
白话：租云上的“电脑毛坯”
云厂商提供：计算、存储、网络
你负责：操作系统、运行环境、应用、数据

第二列：
PaaS
Platform as a Service
平台即服务
白话：租“能直接开发和部署的平台”
云厂商再管：操作系统、运行时、中间件、扩缩容
你负责：代码、应用配置、数据

第三列：
SaaS
Software as a Service
软件即服务
白话：直接使用“做好的软件”
云厂商运行整套应用
你负责：账号、配置、数据治理与正确使用

底部做一条双向趋势轴：
越靠左：控制更强、运维更多
越靠右：开箱更快、底层控制更少

底部结论醒目短句：
不是谁更高级，而是“你想管到哪一层”。

版式要求：标题区约 18%，三列对比约 65%，结论区约 17%；每列文字不拥挤，英文全称字号略小但必须清楚；不要添加本提示之外的段落。
```

## 02 — 共享责任模型

```text
原创中文技术知识卡片，3:4 竖版，浅米白背景，现代云计算信息图风格，深蓝、青绿、橙色区分三种模式，圆角矩阵，清晰矢量图标，留白充足，手机端易读。不要品牌 Logo，不要人物照片，不要水印，不要页码。所有术语、英文、中文必须准确。

主标题：上云之后，谁负责哪一层？
副标题：Shared Responsibility Model（共享责任模型）

用清楚的三列对比表呈现 IaaS、PaaS、SaaS，左侧是技术层级，自上而下：
数据 / 身份 / 配置 / 使用
应用
运行时 / 中间件
操作系统
虚拟化
计算 / 存储 / 网络
物理数据中心

图例：蓝色＝你负责；绿色＝云厂商负责；橙色＝共同责任。

三列责任范围：
IaaS：你负责操作系统、运行时/中间件、应用，以及数据/身份/配置/使用；云厂商负责虚拟化、计算/存储/网络、物理数据中心。
PaaS：你负责应用；数据/身份/配置/使用为共同责任；云厂商负责运行时/中间件、操作系统、虚拟化、计算/存储/网络、物理数据中心。
SaaS：数据/身份/配置/使用为共同责任；应用及其以下各层由云厂商运行。

表格下方用三个短解释：
IaaS：自由度最高，补丁与系统安全也更多由你承担
PaaS：专注代码，平台替你维护运行环境
SaaS：开箱即用，但账号、权限、数据和用法仍不能甩手

底部警示框：
上云 ≠ 把安全全部交给云厂商
无论哪种模式，你都要管好身份、数据访问、配置与合规使用。

层次清楚，不要密集小字，不要把“共同责任”画成云厂商单独负责。
```

## 03 — 如何选 IaaS、PaaS、SaaS

```text
原创中文技术知识卡片，3:4 竖版，浅色背景，现代产品决策信息图，深蓝、青绿、橙色，圆角卡片、流程箭头、简洁线性图标，手机端易读，留白充分。不要品牌 Logo，不要人物照片，不要水印，不要页码。文字准确，不添加无关内容。

主标题：IaaS、PaaS、SaaS 怎么选？
副标题：先问“要用软件，还是要造软件？”

上半部做一个三步决策流程：
第一问：市面上已有成品，需求能通过配置满足？
是 → SaaS
说明：直接用现成业务能力，最快上线

否 → 第二问：要自己写应用，但不想维护操作系统和运行时？
是 → PaaS
说明：专注代码、数据和产品逻辑

否 → IaaS
说明：需要自定义操作系统、网络、运行环境或迁移旧系统

中部三个场景卡：
SaaS（Software as a Service，软件即服务）
适合：邮箱、协作、CRM、标准业务工具
关键词：开箱即用

PaaS（Platform as a Service，平台即服务）
适合：Web/API、移动后端、快速迭代产品
关键词：开发部署更快

IaaS（Infrastructure as a Service，基础设施即服务）
适合：遗留系统、特殊驱动、定制网络、强控制
关键词：控制更细

底部“别踩坑”：
• 不是越靠右越高级，选择取决于控制、速度、成本与团队能力
• 三者可以组合：一个 SaaS 产品，本身也可能构建在 PaaS 和 IaaS 上

底部结论：
能买则买，需要差异化再造；造到哪一层，决定你要管多少。
```

定向修订提示词：

```text
保持原图 3:4 竖版、颜色、字体、卡片、流程箭头、下方 SaaS/PaaS/IaaS 三栏、“别踩坑”和“最终结论”的全部设计与文字不变。只修复顶部右侧编号 3 的空白问题：在服务器图标下加入清晰可读的第三问文字“需要自定义操作系统、网络或特殊运行环境？”，并让第二问的“否”箭头指向第三问，第三问向下自然对应 IaaS 卡片。不得删除其他内容，不得改写任何英文全称，不要新增页码、水印或 Logo。
```

## 04 — 从传统 SaaS 到 AI SaaS

```text
原创中文技术知识卡片，3:4 竖版，浅米白背景，现代 SaaS 产品演进信息图，深蓝、青绿、紫色和少量橙色，圆角卡片、清晰箭头、简洁矢量图标，手机端可读，留白充足。不要品牌 Logo，不要人物照片，不要水印，不要页码。所有中英文准确。

主标题：AI 时代的 SaaS
副标题：从“提供功能”到“理解意图、完成任务”

用从左到右或从上到下的三阶段演进：
① Traditional SaaS（传统 SaaS）
交互：用户点菜单、填表单
核心：固定功能 + 规则流程
特点：结果更确定、容易测试
例子表达：记录、审批、报表

② AI-enabled SaaS（AI 增强型 SaaS）
交互：在原有软件里加入 Copilot（智能副手）
核心：生成、总结、分类、问答
特点：AI 提效，人仍主导流程

③ AI-native / Agentic SaaS（AI 原生 / 智能体型 SaaS）
交互：用户说目标
核心流程：理解意图 → 制定步骤 → 检索信息 → 调用工具 → 执行动作 → 返回结果
特点：从“按按钮”走向“交付任务结果”

中间做一句醒目标注：
AI SaaS 仍然是 SaaS，不是第四种官方云服务模型。

下方对比：
过去：功能中心、席位订阅、用户操作每一步
现在：意图中心、模型 + 数据 + 工具协作、按用量/任务/结果的混合计费可能增加

底部“别盲目 Agent 化”提示：
固定规则能解决的流程，通常更便宜、更稳定、更容易审计；
只有任务需要理解上下文、动态决策或跨系统操作时，Agent 才更有价值。

视觉关系必须表达“逐步增强”而不是三者互相替代。
```

## 05 — AI SaaS 受控执行链

```text
原创中文技术知识卡片，3:4 竖版，浅色背景，严谨但易懂的 AI SaaS 技术架构信息图，深蓝、青绿、紫色、橙色少量强调，圆角模块，箭头清晰，简洁矢量图标，手机端可读。不要品牌 Logo，不要人物照片，不要水印，不要页码。英文术语和中文解释必须准确。

主标题：AI SaaS 是怎么完成一次任务的？
副标题：不是只接一个大模型 API，而是一条受控执行链

中心画一条自上而下的主链路：
用户 / Tenant（租户）
↓
Identity & Tenant Context（身份与租户上下文）
↓
SaaS UI / API（产品入口）
↓
Orchestrator / Agent（编排器 / 智能体）
理解目标、选择步骤、决定是否调用工具
↓
Model Gateway（模型网关）
路由模型、限流、预算、重试
↓
结果与动作

在“编排器 / 智能体”左右连接四个能力模块：
RAG（Retrieval-Augmented Generation，检索增强生成）
从授权知识库取回依据；强调：提供依据，不保证绝对正确

Memory / State（记忆 / 状态）
保存任务上下文；必须限定租户与生命周期

Tool Calling（工具调用）
调用数据库、搜索、邮件、工单、业务 API；使用最小权限

Guardrails（安全护栏）
输入输出检查、敏感数据策略、动作约束

底部做高风险动作闸门：
删除、付款、发布、授权等不可逆操作
→ Human Approval（人工审批）
→ 执行并写入 Audit Log（审计日志）

最底部结论：
模型负责“推理建议”，系统负责“权限、边界与可追溯执行”。

视觉上用大框将整条链路包住，标注：
Observability（可观测性）：日志、追踪、评测、成本、延迟。
```

## 06 — AI Agent 共享责任

```text
原创中文技术知识卡片，3:4 竖版，浅米白背景，现代云安全信息图，深蓝、青绿、紫色和少量橙色，三列圆角卡片、分层栈图标，手机端清晰可读，留白充分。不要品牌 Logo，不要人物照片，不要水印，不要页码。术语和责任边界必须准确。

主标题：AI Agent 上云，责任怎么分？
副标题：服务越“托管”，你少管底层，但不会失去数据与使用责任

用三列从左到右对比：

IaaS Agent
Infrastructure as a Service Agent
基础设施即服务上的智能体
云厂商通常负责：物理基础设施、虚拟化
你通常负责：操作系统、模型/推理服务的部署方式、编排器、记忆、工具、权限、安全控制、应用与数据
适合：强定制、私有部署、底层控制要求高

PaaS Agent
Platform as a Service Agent
平台即服务上的智能体
云厂商通常负责：托管模型、运行时、平台扩缩容、基础平台安全
你通常负责：系统指令、编排逻辑、RAG、记忆、工具/插件、Agent 身份与授权、业务数据
适合：快速构建自己的 AI 产品

SaaS Agent
Software as a Service Agent
软件即服务里的智能体
云厂商通常负责：应用、编排器、模型、安全护栏和内置连接器的运行
你仍负责：租户配置、用户身份、数据访问范围、使用策略、输出复核、合规映射
适合：直接使用成品 AI 业务能力

中部做一条趋势：
IaaS → PaaS → SaaS
你管理的技术栈逐步减少；供应商托管范围逐步增加。

底部醒目提示：
Shared Responsibility（共享责任）仍然成立
• 身份、数据、授权范围和正确使用，不能因为用了 AI SaaS 就完全交给供应商
• 具体边界以产品能力、配置和合同为准

不要声称所有供应商责任完全相同；用“通常负责”字样。
```

## 07 — AI SaaS 风险、成本与治理

```text
原创中文技术知识卡片，3:4 竖版，浅色背景，面向 AI SaaS 产品上线前检查的高质量信息图，深蓝、青绿、紫色、橙红风险色，六个圆角检查模块，简洁矢量图标，手机端可读，留白充足。不要品牌 Logo，不要人物照片，不要水印，不要页码。中文准确，英文术语规范。

主标题：AI SaaS 上线前，算清 6 笔账
副标题：能回答，不等于能安全、稳定、赚钱地交付

六个模块：

01 质量账 Quality
Confabulation（虚构/自信地答错）
做法：基准测试、引用依据、输出复核
提醒：RAG 能增加依据，不保证绝对正确

02 安全账 Security
Prompt Injection（提示注入）、工具滥用
做法：最小权限、参数校验、敏感动作审批

03 租户与数据账 Isolation
隔离：原始数据、向量索引、提示上下文、记忆、工具凭据、日志
提醒：Authentication（认证）≠ Tenant Isolation（租户隔离）

04 成本账 Cost
新增成本：输入/输出 Token、Embedding、检索、工具调用、重试、推理循环、GPU
关键指标：Cost per Successful Task（每个成功任务成本）

05 延迟与可靠性账 Reliability
做法：迭代上限、Token 预算、超时、降级、幂等、故障回退
指标：P95 延迟、工具成功率、人工接管率

06 治理账 Governance
做法：身份权限、数据治理、审计日志、人工复核、合规映射、停用开关
原则：高风险动作先审批，执行过程可追溯

底部做“商业模式变化”横条：
传统 SaaS 常见：按席位订阅
AI SaaS 可能增加：按用量 / 按任务 / 按结果 / 混合计费
强调：不是统一答案，定价要覆盖真实推理成本与业务价值。

底部结论：
AI SaaS 的护城河，不只是模型，而是“可靠数据 + 安全工具链 + 可评测交付 + 可持续成本”。
```
