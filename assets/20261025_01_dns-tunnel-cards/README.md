# 解析、网关、隧道：DNS、OpenClash、Cloudflare Tunnel、Clash 与公司 VPN

## 白话结论

- 域名解析（DNS）只负责“查地址”，不管流量走哪条路。
- 一个内网地址可以同时是“默认网关”和“解析服务器”，改其中一个不等于改另一个。
- 不用网关做解析，网关代理软件的解析分流就不生效；但只要网关没变，流量仍经过网关。
- Cloudflare Tunnel 是“请人进来”：本机主动向外建通道，让公网访客访问本机服务。
- Clash 客户端是“自己出去挑路”：本机按规则选代理节点上网。
- 公司 VPN（OpenVPN Connect）是“回公司上班”：本机加密加入公司内网。

## 技术要点

### 1. DNS 是怎么查的

`DNS (Domain Name System，域名系统)` 把域名翻译成 `IP (Internet Protocol，网际协议)` 地址。`Resolver（解析器）` 是设备实际去问的递归解析服务：它先查缓存，没有缓存就依次问根、顶级域和权威服务器，最后把结果返回给设备。设备上填的解析地址，就是这个“查号台”的地址。

主解析与备用解析不是负载均衡：系统先问主解析，主解析超时或失败才试备用。主解析本身能返回结果（哪怕是错误结果），系统一般不会再问备用。

### 2. 三个解析服务的区别

- `114.114.114.114`：国内 114DNS。国内网站解析快；个别国外域名可能查不到，或返回的结果与国外权威结果不一致。是否支持加密解析、过滤策略，以该服务当前说明为准。
- `223.5.5.5`：阿里云解析（AliDNS）。国内同样快，对国外域名的兼容性通常更好，适合在国内当主力解析。
- `1.1.1.1`：Cloudflare 解析。全球部署，隐私保护承诺较明确（不以查询记录做广告画像）；国内访问要绕到海外节点，速度不稳，个别网络可能拦截，适合当备用。

三者都没有“绝对正确”：解析结果受运营商、地区、缓存和服务策略影响，换解析前先用 `nslookup` 对照验证。

```powershell
nslookup <域名> 223.5.5.5
nslookup <域名> 1.1.1.1
```

### 3. 网关地址的两个身份

`192.168. 开头` 的地址属于私有地址，只在局域网内有效，出了内网没有意义。同一台设备（通常是路由器或旁路由）可以同时承担两个角色：

- `Gateway（网关）`，即默认网关：设备访问外网时，流量先发给它，由它转发出去。改了默认网关，整台设备的出门路线都变。
- `DNS Server（解析服务器）`：只回答“这个域名对应哪个地址”，不转发业务流量。改了它，只换“问谁查地址”，出门路线不变。

查看与修改（Windows，管理员 PowerShell，地址均为示例或占位符）：

```powershell
Get-DnsClientServerAddress -AddressFamily IPv4
Get-NetRoute -DestinationPrefix "0.0.0.0/0"
Set-DnsClientServerAddress -InterfaceIndex <接口编号> -ServerAddresses "223.5.5.5","1.1.1.1"
ipconfig /flushdns
```

改回原解析时，把最后一组地址换回改动前记录的原值，不要凭记忆拼写。

### 4. 不用网关做解析，对 OpenClash / Mihomo 有什么影响

`OpenClash` 是运行在网关（通常是 OpenWrt 路由器）上的规则代理软件，核心是 `Mihomo` 内核。它做两件事：

1. **解析分流**：设备的域名查询被送到 Mihomo 的解析服务。按规则，有的域名返回真实地址，有的返回 `Fake-IP（假地址）`——一段专门留给本地匹配用的地址（常见于 `198.18.0.0/16` 网段，示例），设备随后访问假地址时，Mihomo 再按规则决定直连还是走代理。假地址本身不是目标服务器的真实地址。
2. **流量规则**：按域名、域名后缀、`GEOIP (基于 IP 地理位置的规则)`、最终规则等匹配，决定直连、代理或拒绝。

如果设备不再把网关当解析服务器，改成直接问阿里或 Cloudflare：

- **失效的部分**：网关的解析规则、基于解析的广告过滤、假地址分流不再对这台设备生效。域名解析结果是公共解析给的真实地址，Mihomo 无法再用“解析时返回什么”来分流。
- **还在的部分**：只要默认网关没变，流量仍经过网关，按 IP 的规则、透明代理、流量转发仍在。
- **边界**：如果 Mihomo 开启了 `Sniffer（嗅探器）`，它可能从流量的 `SNI (Server Name Indication，服务器名称指示)` 等特征里识别域名，部分域名规则仍可能匹配，但这不保证、不完整，不能替代解析分流。广告过滤、解析劫持类能力尤其依赖解析环节，绕开后基本失效。

如果连默认网关也改掉（不再走这台网关设备），那才是真正离开这套代理：全部规则失效，流量改走新网关；同时旧网关上的局域网服务也可能访问不到，除非另有路由。

### 5. Cloudflare Tunnel 的原理

`Cloudflare Tunnel（Cloudflare 隧道）` 由本机软件 `cloudflared` 实现：

1. 本机上的 `cloudflared` 主动向外连接 Cloudflare 边缘节点，建立加密通道（优先 `QUIC (Quick UDP Internet Connections，基于 UDP 的快速传输协议)`，受限时回退到 `HTTP/2`）。
2. 访客访问域名时，先到 Cloudflare 边缘，边缘再把请求经这条已建立的通道送回本机服务。
3. 方向是“由内向外建通道、由外向内传请求”，因此不需要在路由器上开入站端口，也不需要把家庭公网 IP 暴露给访客。

关键边界：

- 服务可用性等于本机在线率：本机断电、断网、重启，服务就下线。
- 临时隧道（Quick Tunnel）地址是随机分配的，进程重启地址就变，只适合临时验证。
- 命名隧道（Named Tunnel）绑定固定域名，需要 Cloudflare 账号，并在 Cloudflare 侧为该域名建立指向隧道的记录；域名本身是否需要把解析托管到 Cloudflare，取决于所用的接入方式，以 Cloudflare 当前文档为准。
- 隧道只解决“怎么进来”，不解决“谁能进来”：公开服务仍需应用自身的登录、鉴权与访问控制，同步接口等敏感入口必须保留密钥校验。

### 6. Clash 客户端的原理

`Clash` 客户端（桌面或移动端，核心多为 Mihomo / Clash Meta）是装在本机上的规则代理软件：

1. 本机应用的流量先经过 Clash 核心（系统代理或 `TUN (虚拟网卡)` 模式）。
2. 核心按规则匹配域名、IP、端口、进程等，决定直连、走某个代理节点，还是拒绝。
3. 代理节点之间用各自的代理协议传输，节点负责把请求发往目标服务器并把响应带回。

方向是“向外”：解决的是本机上网“走哪条路”，不负责让别人访问本机。

### 7. 公司 VPN（OpenVPN Connect）的原理

`OpenVPN Connect` 是 OpenVPN 的官方客户端，`VPN (Virtual Private Network，虚拟专用网络)` 的一种实现：

1. 客户端用证书、账号口令或多因素认证向公司 VPN 服务器发起连接，协商加密通道（`TLS (Transport Layer Security，传输层安全协议)` 握手 + 对称加密传输）。
2. 连接建立后，本机多出一块虚拟网卡，获得一个公司内网地址；访问公司内网资源时，流量经加密通道到公司网关，再进内网。
3. 路由分两种：`Full Tunnel（全隧道）` 是全部流量都走公司；`Split Tunnel（分流隧道）` 是只有公司网段走 VPN，其余流量仍直连。具体是哪种，由公司策略决定，员工侧一般改不了。
4. 断开 VPN，本机就离开公司内网，内网资源随即访问不到；公司侧按策略可能记录连接与访问日志。

### 8. 三者对照

| 维度 | Cloudflare Tunnel | Clash 客户端 | OpenVPN Connect 公司 VPN |
| --- | --- | --- | --- |
| 方向 | 向内发布：公网访客访问本机服务 | 向外代理：本机按规则上网 | 向内加入：本机加入公司内网 |
| 谁主动建连接 | 本机服务方向外连边缘 | 本机客户端连代理节点 | 员工客户端连公司服务器 |
| 访客 / 使用者 | 任何能访问该域名的人（除非另加访问控制） | 只有本机（或本机所在局域网） | 只有通过公司认证的员工设备 |
| 加密与身份 | 通道加密；访客身份由应用自己管 | 到节点的通道加密；节点与目标之间按目标协议而定 | 通道加密 + 公司证书 / 账号认证 |
| 断开后 | 公网访问不到本机服务 | 本机恢复直连（或按系统设置） | 本机离开公司内网 |
| 典型用途 | 把家里 / 测试机服务临时公开 | 按规则分流上网 | 远程办公访问公司内网 |

### 9. 排错方法

- 隧道连不上：先看 `cloudflared` 日志里的解析与连接自检；解析失败时，换 223.5.5.5、1.1.1.1 做 `nslookup` 对照；QUIC 受限时，检查出站 UDP 是否被拦截。
- 换解析后某个网站打不开：先确认是解析问题还是代理问题——`nslookup` 能查到地址但打不开，多半是流量侧；`nslookup` 查不到或结果异常，才是解析侧。
- 换解析后代理规则变了：先确认改的是解析还是网关（见第 3 节），再确认网关的解析分流、假地址模式与嗅探开关。
- 改错了解析：用改动前记录的原值改回，并 `ipconfig /flushdns` 清缓存；不要同时改网关和解析，否则分不清是哪一步出的问题。
