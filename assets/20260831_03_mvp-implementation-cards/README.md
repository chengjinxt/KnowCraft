## MVP 是什么

`MVP (Minimum Viable Product，最小可行产品)`：用最小但完整可用的产品范围，验证最关键、最不确定的业务假设。

它不是“随便砍功能后的粗糙版本”。`Minimum（最小）`说的是验证范围，`Viable（可行）`要求用户仍然能够完成核心任务，`Product（产品）`意味着它需要面对真实使用和反馈。

## 五步实施方案

### 1. Core Hypothesis（核心假设）

先写清目标用户、使用场景、真实痛点和预期价值，并明确本次最需要验证的未知因素。

可以使用下面的假设模板：

```text
我们相信：[目标用户]
在：[具体场景]
存在：[需要解决的问题]
使用：[最小解决方案]
能够：[完成核心任务]。

如果：[指标或用户证据]
达到：[预先约定的成功阈值]，
则说明该假设获得初步验证。
```

### 2. Scope（裁剪范围）

- `Must Have（必须有）`：没有它就无法验证核心假设。
- `Later（以后做）`：有价值，但不影响本轮验证。
- `Not Now（暂不做）`：主动排除，防止范围膨胀。

判断标准不是“开发起来是否有趣”，而是“是否直接影响核心假设的验证”。

### 3. Smallest Loop（最小闭环）

至少跑通：`入口 → 核心动作 → 结果 → 反馈`。用户必须能独立完成一件有价值的事情，而不是只能观看 Demo 或停在半流程中。

### 4. Pilot Launch（小范围发布）

把 MVP 交给真实目标用户使用。发布前先确定成功阈值、观察方式和停止条件，避免看到结果后再临时修改判断标准。

### 5. Metrics & Decision（衡量与决策）

结合行为数据和用户反馈做出下一步选择：

- `Persevere（继续）`：核心假设得到支持，继续完善或扩大范围。
- `Pivot（转向）`：需求可能存在，但用户、场景或解决方案需要调整。
- `Stop（停止）`：证据不足以支持继续投入。

## Build–Measure–Learn 闭环

`Build → Measure → Learn（构建 → 衡量 → 学习）`不是只循环写代码，而是每一轮都减少一个关键不确定性。

## 质量红线

MVP 可以减少范围，但不应省略与场景相关的安全、隐私、数据准确、核心流程和恢复能力。涉及支付、账号、敏感数据或不可逆操作时，质量与合规要求不会因为产品处于 MVP 阶段而消失。

卡片中的“MVP 公式”是便于理解的教学表达，不是行业统一的数学公式：

```text
最小范围 × 可用体验 × 可验证学习
Minimum Scope × Viable Experience × Measurable Learning
```
